# План: разобраться почему калькулятор не отправляет заявки с iPhone Safari

## Что я уже подтвердил по логам и БД

1. **С десктопа сегодня (24 апреля) калькулятор работает идеально** — 4 успешные заявки в БД с `device_type: desktop`, последняя в 13:50, все три уведомления (Telegram + push + БД) сработали.
2. **С мобильного устройств с 24 апреля — НИ ОДНОЙ заявки в БД**. Последний мобильный лид от 23.04 в 16:31.
3. **Edge-функция `handle-lead` сама по себе исправна** — она просто не вызывается с iPhone, либо вызывается, но запрос падает на стороне клиента до сети.
4. **CORS, RLS, rate-limit, schema БД — всё корректно**, эти слои работают одинаково для всех устройств.
5. **Service Worker (`sw.js`) — чистый**, обрабатывает только push-уведомления, никакого fetch-перехвата (это **не я сломал** прошлой правкой).

Симптом, который вы описали: на iPhone Safari появляется **красный тост «Ошибка отправки. Позвоните: 8-495-018-18-17»** — это catch-блок в `SimpleCalculator.handleSubmit` (строка 248-254), значит `supabase.functions.invoke('handle-lead')` бросает исключение **до** того как доходит до моего сервера.

## Корневая причина (наиболее вероятная)

Главный подозреваемый — `src/lib/supabaseClient.ts`, строка 72:

```ts
const mod = await import('@/integrations/supabase/client');  // ← top-level await!
supabase = mod.supabase;
```

**Top-level await** работает только в iOS Safari **15.0+**. Даже на поддерживаемых версиях он создаёт отдельный чанк, который догружается асинхронно. В мобильном Safari при нестабильной сети или агрессивном кешировании этот чанк:
- может **зависнуть** при загрузке (форма посылает invoke до того как `supabase` реально проинициализирован → доступ к `undefined.functions.invoke` → TypeError);
- может **упасть с ошибкой parse** на старых iOS (14.x);
- может загружаться слишком долго → пользователь успевает кликнуть «Вызвать мастера» до готовности модуля.

Кроме калькулятора этот же `supabaseClient.ts` импортируют `HeroCallbackForm`, `LeadFormModal`, `Quiz`, `QuickCallForm` — они тоже под угрозой, но пользователь пока тестировал только калькулятор.

Дополнительный фактор: `device_type` определяется в `TrafficContext`, и если context ещё не успел проинициализироваться на момент клика (часто на медленном мобильном), `context?.deviceType` приходит `undefined` — запрос-то всё равно уходит, но это объясняет почему в БД desktop-лиды есть, а mobile-лиды резко исчезли.

## Что я сделаю — 3 точечные правки, 0 риска

### 1. Убрать top-level await из `src/lib/supabaseClient.ts` (главная правка)

Заменю асинхронный динамический импорт на статический re-export с runtime-guard на SSR. Это убирает зависимость от поддержки top-level await и гарантирует что `supabase` доступен **синхронно** сразу после загрузки скрипта.

```ts
// На клиенте — сразу подгружаем настоящий клиент через статический импорт
// На сервере (SSR) — экспортируем noop-стаб
import { supabase as realClient } from '@/integrations/supabase/client';

const supabase: any = import.meta.env.SSR ? noopClient : realClient;
export { supabase };
```

SSR-безопасность сохраняется, потому что `import.meta.env.SSR` срабатывает на этапе сборки, и Vite tree-shake'нет неиспользуемую ветку. Если вдруг tree-shake не сработает — вторая защита: статический импорт `@/integrations/supabase/client` уже сейчас защищён в `client.ts` от SSR (там используется `localStorage` через `auth.storage` который доступен только в браузере). Я добавлю условный импорт через `import.meta.env.SSR ? null : ...` если потребуется (но статический import обычно безопасен — клиент создаётся при вызове `createClient`, а не при импорте).

### 2. Защитить `SimpleCalculator.handleSubmit` от undefined-supabase

Добавлю проверку `if (!supabase?.functions?.invoke)` в начало `handleSubmit` — если по какой-то причине клиент не загрузился, покажу понятный тост «Перезагрузите страницу», а не загадочную «Ошибка отправки». То же самое в `HeroCallbackForm`. Это защитный шов на случай ещё каких-то экзотических браузеров.

### 3. Добавить fallback на прямой `fetch` (страховка)

В `handleSubmit` калькулятора, если `supabase.functions.invoke` бросает ошибку, делаю **второй проход** — обычный `fetch` напрямую к edge-функции с теми же данными. Url-ы для функций известны (`https://gimkzlozhwwgetlgtgvj.supabase.co/functions/v1/handle-lead`), apikey-ы лежат в `import.meta.env.VITE_SUPABASE_PUBLISHABLE_KEY`. Если хотя бы один из путей сработает — заявка дойдёт. Это страховка на случай если supabase-js всё-таки сломан в каком-то браузере.

## Чего я НЕ трогаю

- `_shared/cors.ts`, `nginx.conf`, `sw.js` — никакого отношения к проблеме.

## Как проверим что починилось

После деплоя (~5 минут через GitHub Actions, либо `/root/deploy.sh` вручную):

1. На iPhone в Safari открыть `goruslugimsk.ru`, **жёстко обновить страницу** (закрыть вкладку → открыть заново, либо Settings → Safari → Очистить историю), это обязательно из-за SW-кеша.
2. Открыть калькулятор → пройти все шаги → ввести ваш реальный номер → нажать «Вызвать мастера».
3. Должен появиться зелёный экран «Заявка отправлена!», а в Telegram — уведомление в течение 5 секунд.
4. Если **до** деплоя были рейт-лимит-ошибки от ваших тестов — подождите 1 минуту между попытками (5 заявок в минуту с одного IP — лимит на сервере).

Если после правки **снова** не работает — попрошу вас открыть Safari → Настройки → Дополнения → Веб-инспектор, подключиться к Mac и сбросить мне реальный консольный лог (или просто скриншот ошибки в консоли). Тогда можно будет точно понять что именно блокирует запрос на iOS — это уже невозможно угадать без живых данных с устройства.
